# The approval card

*One card, one action, the exact content pinned on it. When a person taps Approve, the program executes what the card showed. The model is not asked again.*

Written against Claude Code 2.1.240 and lark-cli 1.0.89. The reference implementation is `bridge/approval.mjs`, with one example action in `bridge/actions/write-outside.mjs` and offline tests in `bridge/test/approval.test.mjs`; the code is the truth if this chapter and the code ever disagree.

**What you should see on those versions:**

- A draft the model leaves in `outbox/` becomes a card showing the target, the full content in a code block, "Not yet written", and Approve and Reject buttons.
- The outside folder stays empty until the tap.
- Approve writes the file outside the working directory byte for byte equal to the pinned content (leading spaces and `**bold**` markers included), then repaints the card "Done" and removes its buttons.
- Reject repaints the card "Rejected" and writes nothing.
- `**bold**` markers inside the content's code block show literally, not as bold.

In the Lark client the buttons disappear after the first tap, so a second tap on the same card cannot be made there; the double-tap protection is covered by the offline suite. **Tap one real card on your own test app before trusting it:** your app, client and versions may behave differently.

## When an action needs a card

Read your Writes and Rollback cells ([the eight cells](eight-cells.md)) against four tests. **Any one true means that action goes through a card:**

1. **Someone other than you can see the result.** A message in a group, a post, a row in a shared table, a file other people open.
2. **It touches real money or a ledger.** An invoice, a payment record, a stock count, anything someone reconciles later.
3. **It cannot be undone.** A sent message, a delete, a push, an email.
4. **The value being written was generated by the model**, not a fixed parameter. A drafted reply, a summary written into a record, an amount it worked out.

Test 4 catches the most, and it is the one people skip. A fixed script that copies a file from A to B passes none of the tests; the same script writing a paragraph the model wrote passes test 4, because the paragraph is exactly the part nobody has checked.

## When a card is not needed

- **Read-only actions.** Nothing changes.
- **Messages only to yourself.** The bridge's replies in your own DM are the conversation, not an action.
- **Deterministic, idempotent syncs.** Code copies the same fields from one system to another, keyed by a stable id, and running it twice changes nothing.
- **Values a human already typed and submitted.** If you filled in a form and pressed submit, that press was the approval.
- **Reversible actions.** Give them an undo with a confirm instead. A card on something you can take back in one tap trains you to tap without reading.

A card on everything is as bad as no card: you stop reading them. See the reverse check below.

## The rule: the program executes the pinned card, not the model

The model drafts. The program pins the draft, shows all of it, and on your tap executes exactly that. Nothing between the card and the write asks the model anything, so nothing between them can change.

This is the same idea as the [privileged path](privileged-path.md): the power lives in code you wrote, the model can only choose and draft, and when the effect reaches past you, a person sees the exact content first.

What that rules out:

- asking the model "go ahead" after the tap (it would write a fresh answer, not the one you approved);
- a card that shows a summary while the program executes the full thing;
- a button that says "approve" without saying which draft, so an old card can approve a new one.

## How a draft gets from the model to a card

The model cannot run the action itself. In the reference bridge it has only file tools inside the working directory (README §5), so it has no way to write outside it. What it can do is leave a **draft file** in a fixed folder inside the working directory:

```
<WORKDIR>/outbox/<anything>.json
```

After the run, the bridge (the program, not the model) looks in `outbox/`:

1. It reads only plain `.json` files. A folder, a symlink or a file over 64 KB is refused unread. (A symlink matters: the program runs with more reach than the model, and following a link would let the model make the program read a file the model itself cannot.)
2. It parses each file strictly and validates it against the action's schema.
3. It moves the raw file out of the outbox into the state folder, accepted or not, so the model's exact output is kept as evidence and the same file is never carded twice.
4. It pins the draft: a draft id made by the program, the target worked out by the program, a sha256 fingerprint over everything the card shows, and an expiry.
5. It sends one card for that draft.

If the run failed or was stopped, its drafts are refused, not carded: a draft from a run that did not finish is not something to put in front of a person.

Tell the model the format. For a Claude Code bridge the natural place is a `CLAUDE.md` in the working directory, which Claude Code 2.1.240 loads as project instructions for a run started there, headless `-p` runs included:

```markdown
## Proposing a file outside this folder

You cannot write outside this folder. To propose a file for the owner to approve,
write exactly one JSON file into `outbox/` (any name ending in .json) and nothing else
in it:

{"action": "write-outside", "title": "<one line: what this file is>", "content": "<the exact text of the file>"}

The owner sees the full content on a card and approves or rejects it. Say in your
reply that you proposed it; do not say it was written.
```

`bridge/test/fixtures/` holds two drafts in the exact shape a model writes from this `CLAUDE.md` (a trailing newline on one, none on the other), and the test suite parses both. With this `CLAUDE.md`, a request to save a file outside the working folder leads the model to leave a draft rather than reach for a write it does not have. Your model and version may differ, so capture one draft of your own, add it next to those two, and run the tests before you trust the parser (gotcha 18 in [gotchas.md](gotchas.md)).

A model may put a file name in the title (one of the fixtures has "Shopping list.txt"). The title is only a label on the card; the file is named by the draft id, and the card's Target line shows the real path, so what you approve is what lands.

### The draft file

```json
{
  "action": "write-outside",
  "title": "Meeting notes for Friday",
  "content": "# Notes\n\n- agenda item one\n- agenda item two\n"
}
```

| Key | Rule |
|---|---|
| `action` | Exactly the name of a configured action. The reference bridge has one: `write-outside`. |
| `title` | One line, at most 120 characters. Shown on the card; not written anywhere. |
| `content` | The exact text to write, at most 3,000 characters. |

There is no key for the path or the file name, on purpose. The model never chooses where the write lands: an open output like a path or a recipient is how a card turns into a general shell with extra steps.

### What the parser accepts, and what it refuses

It accepts the ways a real model writes the same JSON: surrounding whitespace, a trailing newline, a UTF-8 byte order mark, Windows line ends, any key order, and one code fence (```` ``` ```` or ```` ```json ````) around the whole thing.

It refuses everything else, each time with a message that says what to fix, sent to the chat the request came from:

- text before or after the fence ("Here is the draft:"), or a fence that does not close;
- anything that is not one JSON object;
- an `action` that is not configured;
- **any key it does not know.** Formatting varies and is accepted; content does not. An extra `"path"` key is not harmless: the model thought it was choosing the path, the program would ignore it, and the card would then show a different target from the one the model described in its reply. Refusing it says so out loud;
- an empty or over-long value, a title with a line break;
- control or invisible characters in the content (a direction override, a zero-width space), because they can make the card show something other than what is written;
- image syntax (`![` or `<img`, in any field), because the Lark platform layer rewrites images into plain text on every card so the card can never make your client fetch a URL, and a draft that is written one way and shown another breaks the whole point of the card. Describe the image or give the plain URL instead; plain URLs and ordinary links pass through unchanged.

**Where else the card could differ from the file.** Image syntax is the only thing `renderCard` in `bridge/platform-lark.mjs` changes, and a test renders a real approval card through it and checks that the content comes out byte for byte. What no offline test can check is how the chat client itself draws the code block. In the Lark client, `**word**` inside the content's code block shows literally. Check these on your client, since the file is written correctly either way and only the display is in question: that leading indentation displays as written, that a fence longer than three backticks is honoured, and that a platform tag (such as a mention tag) inside the block stays plain text. The character count and the fingerprint on the card are the backstop, and the live test below includes a line to check this on your client.

## Card anatomy

```
Approve? Write a new file outside the working folder

Not yet written. Nothing happens until you tap Approve.
Action:   Write a new file outside the working folder
Target:   /full/path/to/outside/draft-mg3k2x1a-9f1c2b7e.md
What it is: Meeting notes for Friday
Current:  no file at this path
New content (exactly what will be written, 45 characters):
  <the whole content, in a code block>
Draft draft-mg3k2x1a-9f1c2b7e · fingerprint 3fa1c09b2d4e · expires 2026-09-26 14:03 UTC

[Approve]  [Reject]
```

- **"Not yet written"** comes first, so nobody reads the card as a report of something done.
- **The full target and the full content**, never a summary. The content sits in a code block so markdown in it is shown, not rendered; the fence is made longer than any run of backticks inside the content, so the content cannot close it early.
- **Current vs new.** For this action the target is always a new file, so "current" is normally "no file at this path". For an action that changes a record, show the current value next to the new one.
- **Both buttons carry the draft id and the fingerprint** (`{kind: "approve", draft, fp}`). A tap whose fingerprint does not match the stored draft is refused.
- **Times in UTC**, labelled, so nobody has to guess the time zone.

## What happens on a tap

Before the tap reaches `approval.mjs`, the loop has already dropped a redelivered tap id and ignored anyone not on the sender allowlist (the tapper's id is the same kind of id as the sender's, so one list serves both; see [runs.md](runs.md#the-stop-button)).

1. **Find the draft** by the id in the button. Unknown: ignored and logged.
2. **Fingerprint.** The button's fingerprint must equal the stored one. If not, nothing runs and you are told in the chat.
3. **State.** Only a `pending` draft can be acted on. A tap on a draft that is already `claimed` does nothing; a tap on one that is `done`, `rejected`, `expired` or `failed` does nothing except repaint that card to its final state (in case an earlier repaint failed and the old card still looked live).
4. **Expiry.** Past its expiry (a day, `TTL_MS`), the draft becomes `expired` and the card closes. What a card shows ages; approve what is current, not what was drafted last week.
5. **Reject** marks it `rejected`, repaints the card as closed, and writes nothing.
6. **Approve claims it.** `pending` becomes `claimed` and is written to disk before anything else happens. The claim has no `await` in front of it, so a second tap, even one a moment later, finds it claimed. Single use.
7. **Execute the pinned draft.** The program checks the stored draft still hashes to its fingerprint, then calls the action with the pinned target and content. The model is not involved.
8. **Read back.** The action reads what it wrote and compares its hash with the approved content. Only a verified write counts as success ([proof.md](proof.md)).
9. **Spent.** The draft becomes `done`, and the card is repainted with the result and **no buttons**.

### Every failure returns the draft

If anything in steps 7 and 8 throws (the disk is full, the target already holds different content, the read-back does not match), the draft goes back to `pending`, the error is recorded, and the card is repainted **with its buttons** and the error on it. A failed attempt never leaves a dead card behind: you can tap Approve again once the cause is fixed, or Reject. After `MAX_ATTEMPTS` failures (3) it stops as `failed`, buttons removed, and asks you to check the target by hand: an unbounded retry is a limit you did not set.

If the bridge dies in the middle of step 7, the draft is left `claimed`. At the next start, `recover()` puts it back to `pending` and repaints the card with a note saying so. That is safe because the action checks before it writes: if the file had already landed, tapping Approve again finds it with the same content, records "already there, not written again", and does not write twice.

If the card itself cannot be sent, the draft is closed as `failed` and you get a plain message saying nothing will be written: a draft nobody can approve should not sit pending.

## The example action: write outside the working directory

`bridge/actions/write-outside.mjs` writes one file into a fixed folder outside the working directory, set by `BRIDGE_OUTSIDE_DIR`. It is the demonstration because it passes test 4 (the content is the model's) and you can check the result with `ls`.

- **The folder is fixed by config** and must not overlap the working directory in either direction. If it were inside, the model could write the "outside" file itself; if the working directory were inside it, the model could read and overwrite what the program wrote. The action refuses to start if they overlap.
- **The file name is the draft id**, a stable id made by the program ([identity.md](identity.md)). Never a name the model picked, never a file name used as an id.
- **Check before write.** Nothing there: write. The same content already there: already done, success without writing. Different content under the same id: an error, never an overwrite.
- **Exclusive, atomic write.** It writes a temp file, then hard-links it to the target, which fails if the target appeared in the meantime. A crash leaves either no file or the whole file.
- **Read back** and compare the hash before reporting success.

To add another action (post into a second chat, add a row to a table), write a second module with the same shape: `name`, `fields`, `describe`, `validate()`, `target()`, `current()`, `execute()`. `execute()` must check before it writes, use the draft id as its stable id in the target (a field on the record, a line in the file), read back after, and throw on anything that is not a verified success. For a post into another chat, the posted message has to carry the draft id somewhere you can look it up; if the platform gives you no way to find a message by it, write that in the Identity cell as a hole.

## Limits

Named constants in `APPROVAL_LIMITS` (`bridge/approval.mjs`) and `WRITE_OUTSIDE_LIMITS` (`bridge/actions/write-outside.mjs`):

| Constant | Value | Why |
|---|---|---|
| `TTL_MS` | 24 h | A card does not hold the queue (unlike a mid-turn relay), so it can wait overnight, but not forever. |
| `MAX_ATTEMPTS` | 3 | Failed executions before the draft stops as `failed`. |
| `MAX_DRAFTS_PER_RUN` | 3 | Drafts carded after one run; the rest are refused out loud. |
| `MAX_DRAFT_FILE_BYTES` | 64 KB | A bigger draft file is refused unread. |
| `MAX_CONTENT_CHARS` | 3,000 | Set by the card, not the disk: the card must show all of it, so a draft too long to show is refused, never cut. |
| `MAX_TITLE_CHARS` | 120 | One line. |
| `SEND_TIMEOUT_MS`, `SEND_RETRIES`, `RETRY_BACKOFF_MS` | 60 s, 2, 2 s doubling | For the card send and every repaint. |

Put these in your Limits cell.

## Wiring it into the bridge

`bridge/bridge.mjs` wires it in, and only when `BRIDGE_OUTSIDE_DIR` is set (an absolute folder outside the working directory; the plist has a commented example). Unset, approval cards are off and nothing in `outbox/` is read. When it is set, `main()`:

1. builds the action with `createWriteOutside({ outsideDir, workdir })`, which refuses a folder that overlaps the working directory;
2. builds the store with `createApproval({ platform, stateDir, workdir, actions })`;
3. calls `approval.recover()` before the bridge starts listening, so a draft left `claimed` by a crash is back to pending before any tap arrives;
4. passes `onOtherCardAction: (a) => approval.handleAction(a)`, so every tap that is not Stop reaches the card after the loop has deduped it and checked the tapper against the allowlist;
5. passes `onJobDone: (job, { state }) => approval.collectOutbox({ chatId: job.chatId, jobId: job.id, runOk: state === 'done' })`, so drafts are collected after each reply and before the next run starts. A job interrupted by a restart is handed to the same hook with its `interrupted` state, so its leftovers are refused rather than carded;
6. on SIGTERM, waits for `approval.settled()` after the bridge shuts down, so a tap that is mid-write finishes its read-back before the process exits.

`handleAction()` never rejects, and the loop also catches anything a card handler throws, because an unhandled rejection in that callback would take the bridge down. The loop hands the tap over on the next tick, not inside the callback itself.

The approval store is `approvals.json` in the state folder, written atomically like the ledger; raw draft files are kept under `approvals/raw/` and refused ones under `approvals/rejected/`. That store is where the Rollback cell finds the records a card produced: each `done` draft names the file it wrote.

## Verifying it

**Offline:** `npm test` runs `bridge/test/approval.test.mjs` against the fake platform, with every tap going through the real loop (so the allowlist and tap dedupe are part of each test). It covers: approve (file written, read back, card spent, buttons gone); a double tap and a redelivered tap (the action runs once, one file); a tap after expiry; a wrong fingerprint; an action failure (draft back to pending, card keeps its buttons, a retry succeeds); the attempt limit; same id with different content on disk (not overwritten); reject, then a late approve on a stale copy of the card; a tap from someone not on the allowlist; a restart between propose and tap; a crash mid-action with the file already written (recovered, approved again, not written twice); a malformed draft file (refused with its message, raw output kept); image syntax refused in any field; a card rendered through the real Lark `renderCard` showing plain URLs, links and fences unchanged; a draft from a run that did not finish; the parser on the two drafts in `bridge/test/fixtures/`, on the other variants a real model can write, and on the things it must refuse; and an outside folder that overlaps the working directory.

**Live, once, on your own test app,** before you trust it:

1. Set `BRIDGE_OUTSIDE_DIR`, restart the bridge, and send this in your DM: "Propose a file outside this folder containing a four line poem about the sea, for my approval." A vague request (such as "propose a file outside") may get a clarifying question instead of a draft. That is not a failure: ask again with the content spelled out. For a second draft, ask for content that holds an indented line, a line of three backticks, and a word in `**stars**`, and check that the card shows all of it literally. Look closely at the indentation: check that leading spaces display as written.
2. Check the card: the full path, the full content in a code block, "Not yet written", two buttons.
3. Tap Approve. Check with `ls` that exactly one file named after the draft id is there, with that content, and that the card now says Done with no buttons.
4. Tap the same card again if your client still shows the old buttons: nothing new should happen. (In the Lark client the buttons disappear after the first tap, so this step usually cannot be done there; the offline suite covers it.)
5. Ask for a second draft and tap Reject: nothing written, card closed.

If a tap does nothing at all, the app is probably missing the `card.action.trigger` callback, which a new app does not have. The bridge's card listener then exits with a `failed_precondition` error that contains a launcher link: open the link and approve it. The listener keeps retrying on its own, so it picks up the callback on its next retry and prints `[event] ready` for `card.action.trigger`; no restart is needed. Details in [lark-setup.md](lark-setup.md#3-what-the-new-app-does-out-of-the-box-and-the-one-thing-it-lacks).

## The reverse check

Once a month, read back the cards from the last thirty days. **If every card was approved unchanged, never refused, never edited, the criteria are too wide.** Narrow the four tests' application for that action (it may be a deterministic sync after all, or reversible and better served by an undo). A card you have stopped reading is no card, and it makes the ones that matter easier to tap through.

The other direction matters too: if a card was refused, ask whether the model should have been allowed to draft that action at all.

## Why not approve each tool call mid-turn instead

Relaying Claude's own permission prompt into the chat is a real option, and some maintained bridges do it. This guide does not default to it, for two reasons: a bot that asks before every step is a bot you stop using, or tap through without reading; and pinning a tool call is weaker than pinning content, because what matters is what lands where others can see it, not which tool wrote it. If you adopt or build a relay anyway, check it against the traps in [build-or-adopt.md](build-or-adopt.md#mid-turn-approval-a-relay-or-a-card).

## Checklist lines this chapter adds

- [ ] Every action in Writes and Rollback read against the four tests; each one that passes a test has a card or a named hole.
- [ ] The model has no tool that can perform a carded action; it can only leave a draft in `outbox/`.
- [ ] The card shows the full target and the full content, "not yet written", and buttons carrying the draft id and fingerprint.
- [ ] On a tap the program executes the pinned draft; the model is not asked again.
- [ ] Single-use claim written to disk before the action runs; a double tap runs the action once (offline test green).
- [ ] Every failure returns the draft to pending with its buttons; success only after a read-back; the card repainted spent with no buttons.
- [ ] Carded writes use the draft id as their stable id: check before, read back after, same id with different content is an error.
- [ ] One real card tapped on your own test app (approve once, reject once) before trusting it.
- [ ] Reverse check done monthly: if every card in thirty days was approved unchanged, the criteria are too wide.
